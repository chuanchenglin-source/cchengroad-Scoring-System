## 1. 背景與目標

### 現況痛點

偵查官系統（小隊長/審計官跨小隊互審工具）目前**只能查看**每個隊伍的計分狀況，**無法進行扣分操作**。CLAUDE.md 的「審計官規則」現行流程是：

> 扣分屬特殊案例 → 群組回報主辦方協助處理

也就是審計官發現違規後，要在 LINE 群組通報主辦方，由主辦方手動處理。這個流程在 5 月活動進入中後段、扣分案例可能增加時，會變成主辦方的工作瓶頸。

### 設計目標

1. 讓偵查官（=審計官）能在系統內**直接記錄扣分**（不必只能通報）
2. **被扣分者能在歷史頁面（history.html）看到自己被扣什麼、為什麼**
3. 整套機制**不污染正式環境**——透過副本測試環境驗證 → PR 給主工程師合併

## 2. 5 個核心設計決策

| # | 決策項 | 結論 |
|---|---|---|
| 1 | **扣分資料存哪** | 偵查官系統自己的 Sheet（避免污染計分 Sheet 紅線） |
| 2 | **扣分綁定什麼** | 一筆扣分 = 某人某天某 box 被扣多少（最小單位） |
| 3 | **生效時機** | 立刻生效（不需審核），含撤回機制 |
| 4 | **撤回權限** | 偵查官能撤自己扣的、主辦方能撤所有；不刪除，改狀態欄位 |
| 5 | **history.html 顯示** | 嵌入對應 box 卡片內，同時頂部總分與週積分都扣除 |

## 3. 雙系統契約

### 3.1 扣分記錄表（在偵查官副本 Sheet `1_bkaXc...` 的「扣分記錄」分頁）

| 欄位 | 型別 | 範例 | 說明 |
|---|---|---|---|
| 扣分編號 | 流水號 | 1 | PK，自動產生 |
| 被扣人ID | 文字 | `T011_周子維_嘉家久` | 對應計分系統 members.id 格式 |
| 填分日期 | 日期 | 2026-05-12 | 被檢核的那一天（YYYY-MM-DD） |
| Box編號 | 數字 | 5 | 1~14 對應 history.html 的 box |
| 扣分數值 | 數字 | 20 | 統一存正數，UI 顯示時加負號 |
| 扣分原因 | 文字 | 「心得文字疑似 AI 生成」 | 偵查官填寫 |
| 偵查官ID | 文字 | `T021_某某_某某` | 紀錄誰扣的 |
| 扣分時間 | 時間戳記 | 2026-05-13 14:30 | 自動產生 |
| **狀態** | 文字 | `active` / `withdrawn` | 撤回不刪除，改狀態 |
| 撤回者ID | 文字 | 可空 | 撤回時填 |
| 撤回時間 | 時間戳記 | 可空 | |
| 撤回原因 | 文字 | 可空 | 「對象寫錯」 |

### 3.2 偵查官副本要做的事

- **扣分輸入介面**：偵查官選某人某天某 box → 填扣分數值 + 原因 → 寫入「扣分記錄」分頁
- **撤回介面**：偵查官看到自己扣的清單可撤回（改狀態為 `withdrawn`）；主辦方看到所有人扣的可撤回任何
- **身分驗證**：複用現有偵查官系統的登入機制

### 3.3 計分系統副本要做的事

- **`webApp.js:getPersonalHistory()` 改造**：
  - 開啟偵查官 Sheet（`SpreadsheetApp.openById('1_bkaXc...')`）
  - 讀「扣分記錄」分頁，過濾 `被扣人ID = userId` 且 `狀態 = active`
  - 把扣分資料附帶到回傳結構（例如 `record.deductions = [{box, score, reason, monitor}]`）
- **`history.html` 改造**：
  - 在 box 卡片表格內，該天若有扣分，顯示紅色警示行「⚠️ 偵查官扣分 -X：原因（偵查官：XX）」
  - `calculateSummary()` 計算總分時減去 active 扣分
  - 週選取器內「積分」同步扣除
  - 被撤回（`withdrawn`）的扣分**不顯示**

### 3.4 設計原則：扣分是獨立負分項目

**扣分記錄不修改原本的 box 分數**，是「附加在原填分上的負分項目」。

範例：W3 box5 原本填 +20，被扣 20 →
- 資料：「box5: +20」**加上**「扣分記錄: -20, 原因」
- 顯示：UI 同時呈現「填 +20」與「扣 -20」，總分計算才扣掉
- 撤回扣分時，只刪扣分記錄，不會影響原 box 填分

理由：透明、可追溯、撤回乾淨。

## 6. 需要與主辦方對齊的事項

CLAUDE.md 寫「扣分屬特殊案例 → 群組回報主辦方協助處理」這條規則，與本設計「**偵查官立刻生效**」並不完全一致。建議實作前先跟主辦方確認：

1. 主辦方是否同意改為「偵查官直接扣 → 事後審查 + 撤回」流程？
2. 撤回/最終裁量權給特定主辦方？（誰能在介面上點撤回）
3. 是否保留「LINE 群組通報」當補充管道（給有爭議案例）？

**這個對齊不阻塞技術實作**——可以一邊做、一邊跟主辦方溝通。
