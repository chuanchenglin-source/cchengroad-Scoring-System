# Supabase 遷移評估報告

**日期**：2026-04-19
**撰寫**：Johnson（協作開發）
**對象**：主工程師參考

---

## 背景與動機

目前系統使用 Google Sheets + Apps Script 架構，隨著活動規模（約 400 人）與計分邏輯複雜度提升，遇到以下痛點：

| 痛點 | 說明 |
|---|---|
| 資料結構難管理 | 大隊→小隊→隊員的階層關係靠欄位對應，容易出錯 |
| 計分邏輯複雜 | Sheets 公式越來越難維護（加總、條件加分、平均等） |
| 儀表板不直觀 | Looker Studio 設定繁瑣，非技術人員難以維護 |

本報告評估是否以 **Supabase** 取代 Google Sheets 作為資料庫。

---

## 現有技術架構（已分析正式 Web App）

```
Google Sheets（資料庫）
      ↕
Google Apps Script（後端邏輯 + Web App）
      ↕
Looker Studio（報表儀表板）
```

**前端技術**：HTML + Tailwind CSS + Vanilla JavaScript
**前後端溝通**：`google.script.run`（Apps Script 專屬 API）
**後端函式**：getMemberList、saveForm、getPersonalHistory、getUserStatus、rebuildSummaryReport 等

---

## 遷移後架構（建議方向）

```
Supabase（PostgreSQL 資料庫 + 自動 REST API）
      ↕
前端（HTML + Tailwind CSS，Vercel 部署）
  ├── 隊員填表頁
  ├── 個人歷史頁
  ├── 小隊長 Dashboard
  ├── 大隊長 Dashboard
  └── 審計官頁面
```

**不需要額外後端伺服器**：Supabase 自動產生 REST API，前端用 Supabase JS SDK 直接讀寫資料。

---

## 各層變動幅度

| 層 | 現況 | 遷移後 | 工作量 |
|---|---|---|---|
| HTML / CSS 樣式 | Tailwind CSS | **完全保留** | 無 |
| 前端 JS 邏輯 | `google.script.run` | 改 Supabase JS SDK | 中 |
| 後端邏輯 | Apps Script 函式 | **Supabase 自動 API 取代，不需重寫伺服器** | 中 |
| 資料庫 | Google Sheets | Supabase PostgreSQL | 高（含資料表設計） |
| 部署平台 | Google（內建） | Vercel（免費） | 低 |
| 儀表板 | Looker Studio | **自建 Dashboard 頁面（Chart.js，免費）** | 中 |

---

## 400 人規模評估

| 面向 | Google Sheets 現況 | Supabase |
|---|---|---|
| 資料量承載 | ✅ 撐得住 | ✅ 免費方案即可（500MB，遠超需求） |
| 多人同時填表 | ⚠️ 可能資料衝突 | ✅ 資料庫層級鎖定，不衝突 |
| 複雜計分邏輯 | ⚠️ Sheets 公式難維護 | ✅ SQL 更適合條件聚合運算 |
| 階層資料結構 | ⚠️ 欄位對應，容易錯 | ✅ 關聯式資料表，天生適合 |
| 開發門檻 | 低（Apps Script 即可） | 中（需熟悉 PostgreSQL + 後端框架） |

## 儀表板方向

**採用自建 Dashboard 頁面**（排除 Looker Studio，設定介面過於複雜）

- 直接在現有前端專案新增頁面（小隊長頁、大隊長頁、審計官頁）
- 使用 **Chart.js**（免費圖表套件）呈現分數統計
- 資料直接從 Supabase 讀取，不需第三方儀表板工具
- 部署在同一個 Vercel 專案，不需額外費用

**好處**：版面與功能完全依照需求客製，不受第三方工具限制。

---

## 遷移風險與建議

### 主要風險
1. **資料表設計需要規劃**：Sheets 的欄位結構要轉換成關聯式資料表，需要事先設計好
2. **`google.script.run` 無法在非 Apps Script 環境使用**：前端 JS 需對應改成 Supabase SDK
3. **時間成本**：估計需要 2–3 週完整建置（含測試）

### 降低風險的策略
- **分階段遷移**：先換資料庫（Supabase），後端暫時透過 API 橋接，前端不動
- **保留現有系統**：遷移期間兩套並行，確認穩定後再切換
- **從新活動開始**：不需要遷移舊資料，直接用新架構建新系統

## 結論與建議

| 問題 | 答案 |
|---|---|
| Supabase 能解決痛點嗎？ | ✅ 是，特別是資料結構與計分邏輯 |
| 400 人規模適合嗎？ | ✅ 免費方案綽綽有餘 |
| 工程量大嗎？ | ⚠️ 大，幾乎是全系統重建 |
| 建議這屆就換嗎？ | 視主工程師時間與意願而定 |

**建議做法**：若主工程師有意願，以「這屆活動開始前」為目標，利用現有 HTML/CSS 樣式基礎重建後端與資料庫。若時間不足，建議這屆先撐完，下屆以新架構重建。
