# 親證班計分系統效能優化提案：加 ScriptCache

**日期**: 2026-05-28
**對象**: 主辦團隊 + 主工程師（joanne19940224）
**範圍**: 副本 0527_泉成（測試環境）驗證後，透過 PR 合併到正式版
**對應 Spectra change**: `add-cache-for-hot-reads`（已 parked，討論後再決定是否實作）

---

## 一、目前的問題

過去兩週收到的回饋有兩個明顯痛點：

### 1. 進入網站變慢（第 4 週後感受明顯）
使用者點「查看歷史紀錄」要等 5-10 秒才看到內容。隨著週數增加會更慢，預計第 8 週末會到 10-20 秒。

### 2. 週六晚上填表大延遲
每週六大量參加者一次把當週分數填完，造成填表提交時要等很久。

### 主辦團隊的初步想法
主辦提議：把「每日個人分數結算」工作表拆成 2 週一張，共 4 張獨立 sheet，希望能分散壓力。

---

## 二、根因分析（驗證後發現的真相）

經過程式碼比對，**慢有三個獨立瓶頸**，跟主辦想像的不太一樣：

| # | 慢的位置 | 真正原因 | 拆 sheet 有幫助嗎？ |
|---|---|---|---|
| A | 進入歷史頁面慢 | 程式每次都讀「每日個人分數結算」**整張表**（4 週時約 117 萬個儲存格）進記憶體，再找出自己那 28 列 | ⚠️ 邊際幫助 |
| B | 週六晚上填表慢 | 填表寫的是「**親證班填分回應**」（依大隊分頁），跟「每日個人分數結算」**完全無關**。真正瓶頸是程式每次填表都重新讀「大隊對照表」一次 | ❌ **完全無關** |
| C | 排程跑很久 | 每天 00:00 重建「每日個人分數結算」，整張表清掉重寫 | ⚠️ 邊際幫助 |

### 拆 sheet 評估

| 對症性 | 拆 4 張 sheet 的效益 |
|---|---|
| 進入網站慢 | 從 1 個大 API call → 4 個中 API call。Google Sheets API 每次有約 500ms-1s overhead，可能反而變慢 |
| 週六填表慢 | **完全沒幫助**（不同表）|
| 排程慢 | 寫入儲存格總數不變，無顯著差異 |

**結論：拆 sheet 不是 root cause 解法。**

---

## 三、提議的解法：加 ScriptCache（記憶體快取）

Apps Script 有內建的 `CacheService.getScriptCache()`，可以把計算結果暫存在記憶體裡，下次同樣的查詢直接拿快取、不用重讀。

### 改動概要（3 個快取 + 1 個失效機制）

```
┌─────────────────────────────────────────────────────────────┐
│ 快取 1：getTeamMap（解週六填表慢的部分）                    │
│ ────────────────────────────────────────                    │
│ 現況：每次填表都重讀「大隊對照表」                          │
│ 改後：第一次讀完存快取（10 分鐘），後續直接命中              │
│ 效益：每次填表省 1-2 秒                                      │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ 快取 2：getPersonalHistory（解進入歷史頁面慢）              │
│ ────────────────────────────────────────                    │
│ 現況：每次點「查看歷史」都讀全表 117 萬格 → 5-10 秒          │
│ 改後：第一次讀完存快取（5 分鐘，per user），             │
│       同一使用者再次點馬上顯示（< 1 秒）                     │
│ 效益：5-10 秒 → 50 毫秒（200 倍加速）                       │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ 快取 3：getWeeklyScoreDetails（解週分數頁慢）              │
│ ────────────────────────────────────────                    │
│ 同上原理，per user 5 分鐘                                    │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ 失效機制：排程跑完後自動清快取                              │
│ ────────────────────────────────────────                    │
│ rebuildSummaryReport 跑完 → 版本號 + 1 → 舊快取自動失效     │
│ 使用者下次查歷史會看到最新資料（不會永遠看到舊資料）         │
└─────────────────────────────────────────────────────────────┘
```

### 跟拆 sheet 的對比

| 項目 | 拆 4 張 sheet | 加 ScriptCache |
|---|---|---|
| 進入網站慢 | ⚠️ 可能變慢 | ✅ 5-10 秒 → 0.05 秒 |
| 週六填表慢 | ❌ 完全無關 | ✅ 省 1-2 秒/次 |
| 排程慢 | ⚠️ 無感 | ⚠️ 無感（本提案不處理）|
| 改動程式範圍 | 大（schedule.js 寫入邏輯整個重構）| 小（約 30-50 行加快取包裝層）|
| 對「親證班計分系統」資料結構影響 | 結構變動（多 3 張 sheet）| 完全不變 |
| 回退（Rollback）難度 | 中（要把多張 sheet 合回去）| 低（清掉快取就回到現況）|

## 四、改動範圍（給主工程師審視用）

### 修改的檔案（只動 2 個）

1. **webApp.gs**（後端腳本）
   - 新增 3 個 private helper：`_getCacheVersion` / `_bumpCacheVersion` / `_cacheKey`
   - 改 `getTeamMap` → 加 cache 包裝
   - 改 `getPersonalHistory` → 加 cache 包裝
   - 改 `getWeeklyScoreDetails` → 加 cache 包裝

2. **schedule.gs**（後端腳本）
   - 改 `rebuildSummaryReport` 結尾 → 呼叫 `_bumpCacheVersion()` 觸發失效

### 不動的東西

- ❌ 不動 main.html / Index.html / history.html / weekly_score.html / admin.html / personal_log.html 任何前端
- ❌ 不動 saveForm 寫入「親證班填分回應」的路徑
- ❌ 不動計分邏輯（上限、去重、加分題、團隊動能）
- ❌ 不動「親證班計分系統」與「親證班填分回應」兩張 Sheet 的欄位結構
- ❌ 不動正式環境（先在副本 0527 驗證、主工程師 review 後才合併）

## 五、預期效益（量化）

| 操作 | 現況 | 加快取後 | 加速倍數 |
|---|---|---|---|
| 第 1 次點「查看歷史紀錄」 | 5-10 秒 | 5-10 秒（cache miss）| 1× |
| 第 2 次點同一頁（5 分鐘內） | 5-10 秒 | < 50 毫秒 | **100-200×** |
| 週六填表（getTeamMap 部分） | 1-2 秒/次 | < 50 毫秒/次 | **20-40×** |
| 排程跑完後第一次看歷史 | 5-10 秒 | 5-10 秒（cache miss）| 1× |

**整體使用者感受**：第一次進入網站仍會等 5-10 秒（這是現況），但**第二次以後操作幾乎即時**。

## 六、風險與緩解

| 風險 | 緩解 |
|---|---|
| 使用者剛填完表單、立刻看歷史，會不會看到舊資料？ | 不會：因為「每日個人分數結算」本來就是每天 00:00 排程才更新（使用者本來就要等隔天才看到自己今天的分數）— 快取不會讓這件事變更糟 |
| 快取資料超過 100KB（Apps Script 限制） | 預估每人歷史資料 10-30KB（遠低於 100KB）。程式內加保護：寫入失敗時記錄警告、回傳原始結果，使用者不會看到錯誤 |
| 快取失效機制壞掉 | 快取最多 5-10 分鐘自動到期，最壞情況使用者看到 5-10 分鐘前的資料（可接受） |
| 多人同時觸發排程 → 版本號競爭 | Apps Script 內 `PropertiesService` 是原子操作，採「最後寫贏」可接受，版本號錯 1 不影響快取正確失效 |

## 七、驗證計畫（副本 0527_泉成 環境）

### 步驟
1. **本機改 2 個檔** → clasp push 到副本 GAS
2. **副本 Apps Script「執行記錄」驗證**：手動觸發一次 `rebuildSummaryReport`，看 log 出現 `[cache] version bumped 0 -> 1`
3. **副本 Web App 驗證**：
   - 開瀏覽器登入副本（任一人員，如 T011_周子維_嘉家久）
   - 點兩次「查看歷史紀錄」— 第二次明顯變快（< 1 秒）
   - 連續提交兩次 saveForm — Apps Script log 顯示第二次 getTeamMap 是 HIT
4. **失效驗證**：手動再跑一次 `rebuildSummaryReport`，立刻看歷史 — 應該回到 5-10 秒（cache miss 重抓）

## 八、本次「不做」、保留為後續優化

| 項目 | 為什麼這次不做 |
|---|---|
| `getPersonalHistory` 改用 lookup by index（只讀該 user 的 row）| 效益更大（從 117 萬格 → 28 × 90 = 2500 格），但要驗證 index 對齊。獨立 change 處理 |
| `rebuildSummaryReport` 改 incremental update（不重寫整表）| 治本之道但風險高（要設計 idempotent 標記）。獨立 change 處理 |
| 拆「每日個人分數結算」為多張 sheet | 不對症（前面分析過）。**保留為 fallback**：若加快取後仍不夠快，再評估 |
